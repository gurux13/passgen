# genpw.cc Chrome extension

Manifest V3 extension. All trust comes from **hardcoded SHA-256 hashes** in `src/pinned.js`. They are
generated from `py/static` and `py/templates` and ship inside the extension. The extension never learns
or caches hashes at runtime: the only way to change them is to release a new extension version.

1. **Verifies genpw.cc and its mirror (passgen.ddns.net).** On those sites a content script re-hashes
   every script, stylesheet and other same-origin resource the page loaded. It also checks the inline
   `<script>` blocks and `on*=` / `javascript:` handlers. Everything is compared with the hardcoded
   hashes. Any script or stylesheet that is unknown, altered, or loaded from another site fails. The result
   is shown as a badge on the toolbar icon (✓ / ✗) and, if anything is off, as a red banner on the page
   (click it for the list of issues).
2. **Signs in to genpw.cc** from the popup with your genpw.cc username and password (hashed exactly
   like the site's login form does). "Stay signed in" stores the login hash (not the password) so the
   extension can renew the session after a browser restart.
3. **Generates and fills passwords on other sites.** When a frame shows a password field and one of
   your genpw.cc resources is named after that site (or a parent domain of it), a small prompt opens in
   the corner. On any other site, press **Fill** in the extension popup. The prompt lets you:
   - choose the resource: the page's domain hierarchy (`login.example.co.uk`, `example.co.uk`) plus any
     existing resources for the site,
   - pick or type the account (prefilled from the resource's last used account, or from what's already in
     the page's username field),
   - edit the params (length, revision, character sets),
   - and fill. Afterwards the extension saves it to genpw.cc like the site's Generate button does (new
     resource/account, changed params, last used). With **Remember login URL** (on by default) the
     resource's URL becomes this page's URL. The URL is only a bookmark: it plays no part in matching.

   The password is generated by genpw.cc's own `sha.js` + `crypto.js`, packaged unmodified with the
   extension (the repository keeps one copy, in `py/static/js`; the sync script copies them into the
   gitignored `extension/generator/`). No code is downloaded at runtime. The packaged files aren't hash-checked at runtime, since they're part of the
   extension itself (Chrome verifies store installs). `crypto.js` is pinned for the sites, though, so a ✓
   on genpw.cc also means the site generates exactly the same passwords as the extension.

All site assets are self-hosted under `py/static`, nothing from CDNs: AngularJS 1.4.9 is vendored as
`static/ext/angular-1.4.9.min.js`, and the Roboto fonts as `static/fonts/roboto/`.

## Security notes

- **genpw.cc pages can only load what's pinned.** Using `declarativeNetRequest`, the browser cancels every
  request a genpw.cc / mirror page starts (by initiator, and per tab, so sandboxed frames are covered too),
  except:
  - the pinned static files,
  - GETs to the read-only endpoints (`/batchresources`, `/commonaccounts?count=N`),
  - navigations to the site's own pages (no query string), login/register form posts, and the exact URLs of
    your saved resources.

  This blocks exfiltration to other sites (including through navigation URLs), injected scripts (e.g.
  Cloudflare's bot detection), frames, websockets, beacons and service workers.
- **API writes carry only legitimate values.** POSTs to `/generated`, `/newsha`, `/newurl`,
  `/updateresource` and `/deleteresource` can't be sent by the page. A small shim (`content/xhr-shim.js`)
  hands them to the extension, which checks every key and value (`src/payload.js`) before sending the
  request itself. Each value must be data the server already has for you, text you actually typed (trusted
  input only, never the master password field), or a site default. No value may contain the master
  password, and the `newsha` hash must be the real hash of the master password you typed. Rejected requests
  aren't sent and show as ✗. Login/register form posts can't be held back (they're navigations), but their
  fields are checked and flagged too.
- **The page can't hide the result.** The verdict combines the page-side report (recorded from
  `document_start`, so code removed after running is still seen) with what the background observed on the
  network. On ✗ the tab is taken to the extension's own warning page ("Close tab" / "Proceed anyway"). The
  badge starts as "…" and fails closed: no complete report within 10 s means ✗.
- **Limits.** Chrome doesn't let an extension see the exact bytes a page received (short of the debugger
  API), so a malicious *server* could still serve different bytes to the page and to the hash check, or
  an inline script could rewrite itself while running. Top-level navigations aren't blocked.

- **Domain matching** (`src/hosts.js`) uses the resource *name*, which is part of the password, never the
  stored URL, so a changed URL on the server can't redirect a password to another site. The page hostname
  must equal the name or be a subdomain of it, on a label boundary (`login.example.com` matches
  `example.com`; `evilexample.com` and `example.com.evil.net` do not). A leading `www.` is ignored. Names
  that aren't domains (e.g. `fs`) never match automatically. Only https pages are filled.
- The page origin comes from Chrome (`sender.origin`), not from the page. The fill message goes back to
  the exact document that asked (`documentId`), and the content script refuses it if its origin changed.
- The master password is typed into an extension-origin iframe; the website cannot read it.
- The generator code runs in `sandbox/generator.html`, which has no extension APIs, and its CSP
  (`default-src 'none'; script-src 'self'`) gives it no network access and no `eval`.
- The master-password hash (first 4 hex of SHA-1, as on the site) is compared with the saved one. On a
  mismatch you must press Fill a second time.

## Install (unpacked)

1. `python extension/tools/sync_ethalon.py` (packages the generator scripts into `extension/generator/`).
2. `chrome://extensions` → enable *Developer mode* → *Load unpacked* → select this `extension/` folder.
3. Click the toolbar icon, sign in with your genpw.cc account.

## Releasing after a site change

1. Change files in `py/static` / `py/templates`.
2. `python extension/tools/sync_ethalon.py` (regenerates `src/pinned.js` and `extension/generator/`).
   Each file pins a **list** of accepted hashes: the new ones are added in front and the previous
   release's stay accepted (up to 4 per file), so the sites and the extension can be updated in any order.
3. Bump `version` in `manifest.json`, push, and release the extension (zip the `extension/` folder,
   including `generator/`; `tests/` and `tools/` aren't needed).
4. Deploy the same files to genpw.cc and passgen.ddns.net.
5. Once every site serves the new files, `python extension/tools/sync_ethalon.py --drop-old` and release
   again to stop accepting the old ones.

**Updates:** when a genpw.cc page fails verification, a Chrome Web Store (or policy) install asks the
store for an update (`chrome.runtime.requestUpdateCheck`). If one exists, the warning page, popup and banner
say "Updating the extension to 1.7.0…", the update is applied right away, and the genpw.cc tabs are
reloaded and checked again with the new pins. Unpacked installs never update on their own: pull, run
the sync script and reload the extension.

**Chrome Web Store:** the extension runs no remotely hosted code: every script it executes is in the
package, and the sandbox has no `eval`.

## Tests

```bash
python -m http.server 8765 --bind 127.0.0.1
```

Then open <http://127.0.0.1:8765/extension/tests/test.html>. The tests cover:
- domain matching
- page verdicts
- hardcoded hashes vs. the repo files
- the packaged generator files are byte-identical to `py/static/js`
- generator parity: the sandbox vs. the site's `<script>` tags
- API payload validation, the master-hash computation and the request allowlist rules
